核心思路

像人读长文档一样检索：先看目录，判断答案在哪一节，翻到那一节读原文，再作答并标注出处。

常见的向量 RAG 把文档切成固定大小的块，按「和问题像不像」取回。这有两个毛病：切块会把一张表、一段论证切断；「语义相似」也不等于「能回答问题」。比如问预算总额，命中的往往是提到"预算"最多的段落，而不是那张汇总表。

pidx 的做法：

  • 建索引时，为每份文档生成一棵章节树。每个节点有标题、页码范围和摘要，节点的原文是按位置精确切出来的，所以一节就是一个完整的检索单位，不会被切断。
  • 检索时由 LLM 推理该读哪几个节点：它读树的骨架（标题 + 页码 + 摘要），再读选中节点的原文作答。树大了以后，先用节点向量召回最相关的几棵子树，LLM 只并行读这几棵子树，而不是整棵树。向量只负责缩小范围，选节点仍由 LLM 决定，取回的单位仍是完整的章节，而不是切块。
  • 支持 PDF、图片、Word / PPT / Excel，以及带目录层级的 zip 资料包：目录本身成为树的上层节点，每个文件是一棵子树。
  • 答案中的论断会附上版面块引用（页码 + 坐标框），点开就能在原页上高亮。引用是 LLM 按提示词加的，大多数论断都会带，但不保证每一句都有。

总览

树检索读的是 SQLite 里存好的树。建索引时花的 LLM 调用是一次性的，之后每次提问通常只要 2–4 次调用。演示页会实时展示每一步，并在最后给出延迟瀑布图。

建索引

① 解析 pidx/parse.py

把文件变成「页 → 版面块 → 行」。PDF 和图片的每个块有坐标框，后面的引用和高亮都靠它；Office 文件没有版面坐标，引用只能定位到块的文本。

情况做法
文本型 PDF用 PyMuPDF 取出字符片段（span），按垂直位置重组成行。有些老 PDF 会把每个单词拆成一"行"，重组能修好这个问题。字号不可信（比如 TeX 字体报 0.1）时，改用字形高度。每行记下字号、是否粗体、所属块、在页文本里的字符偏移。
页眉页脚出现在页面上下各 8% 区域、并且在 ≥25% 页上重复的行（比较前先把数字归一），以及页码，都从正文里去掉。这样它们不会混进节点原文，也不会被误当成标题。
扫描件平均每页不到 80 个字符就判为扫描件，转交 mineru.net 的云端 MinerU（OCR + 版面分析）；单文件上限 200 页，超出的在本地切段后分别上传，结果再按页码拼回。MinerU 的 content_list 会带出标题层级、表格（HTML）、图片和图表的说明文字，坐标从 0–1000 换算回 PDF 坐标。也可以用 mode=ocr 强制走这条路。
图片
png jpg jpeg jp2 webp gif bmp		上传时用 Pillow 包成单页 PDF（gif 取第一帧，150 dpi），之后完全按扫描件处理：MinerU OCR，引用能在原图上画框。
Office
doc docx ppt pptx xls xlsx		原文件直接交给 MinerU 解析，不转 PDF。MinerU 对 Office 不给坐标：Word 整篇是一页，PPT 一张幻灯片一页，Excel 一个工作表一页；Word 的标题样式会给出标题层级，表格是 HTML。pidx 把它们切成虚拟页：每页约 1500 token，尽量在标题前断开；表格转成 markdown，超长的表按行拆开并重复表头。Markdown / txt 走同一条路，但在本地解析，不经过 MinerU：# 标题给出层级，管道表格保留为表格。PPT / Excel 的页带标签（「幻灯片 3」「工作表 2 · 电站清单」）。之后建树、摘要、检索都和 PDF 一样，只是没有页图，引用打开的是解析出的文本。
图像理解
图片、PDF 里的图		解析之后、建树之前，视觉模型（默认 DeepInfra 上的 Qwen/Qwen3.5-35B-A3B）看每张图：先抄下图里的文字和数字（标题、坐标轴、图例、表格单元），再用几句话描述它画的是什么、有什么趋势。图片文件看整张图；PDF 看位图块，以及路径足够多的矢量图区域（图表、示意图；表格框线不算），面积至少占页面 3%，每份文档最多 30 张，按面积从大到小。识别结果作为 figure 类型的版面块插在图在阅读顺序里的位置，带图的坐标框，所以建树、摘要、向量、作答都能用上，引用时能在原页上框出这张图。没配 key 时跳过。一张图约 10 秒、约 $0.0005，并发 8。

② 建树 pidx/tree.py

按可靠程度从高到低依次尝试，前一种不成立才用下一种：

策略 1PDF 书签：至少 3 条，并且 ≥90% 的书签按页码递增，才认为可信。每个书签标题会在它所在页上做模糊匹配（相似度 ≥0.8，允许跨 4 行），定位到具体的行，所以节点能从页中间开始。
例：美联储年报自带 50 条书签，直接成树。

策略 2版面候选 + LLM 定结构：先算出正文字号（按字符数加权的众数），比正文大 ≥0.9pt 的行、块首的短粗体行、MinerU 标出的标题都作为候选。去掉目录页里带引导点的行，跨行的标题合并，重复出现 3 次以上的文字剔除。然后把候选列表（编号 | 页 | 字号 | 粗体 | 文本）交给 LLM，让它挑出真正的章节标题并定层级。如果前 20 页里有目录页，目录全文也一起作为提示。
LLM 只能返回候选编号，不能自己写标题的位置，所以每个标题都锚定在真实的一行上，不会出现幻觉章节。
例：Disney 财报没有书签，26 个候选 → 1 次 LLM 调用 → 26 个节点。

策略 3LLM 直接读页：版面没有可用信号时才用（例如字体信息坏掉的 PDF）。按每组约 1.2 万 token 把页文本带页号标签交给 LLM，让它列出各页开始的标题；每个标题都要回到声称的页（±1 页）上定位，找不到就丢弃。
例：four-lectures.pdf 的字号全是 0.1，走这条路得到 43 个节点。

兜底：三种都失败时，每 10 页一个节点。第一个标题之前如果还有超过 200 字的内容，补一个 Preface 节点。

节点的边界是精确位置 (页, 字符偏移)：节点从自己的标题开始，到下一个同级或更高级标题结束。start_index / end_index 是根据位置算出的页码范围，节点原文按位置切片，所以同一页上的两个小节不会互相串文。

③ 拆分超长节点

超过 10 页或 2 万 token 的叶子节点，太粗，检索时读不准，所以在它的范围内递归再建一层（最多 3 层）。做法和上面一样：先用放宽的候选条件（比正文大 ≥0.5pt，或者是 1.2 / A. / Item 7 / 第三章 这样的编号行），让 LLM 只挑这一节的子标题；不行就退回策略 3。至少拆出 2 个子节点才采用。

例：美联储年报的书签里，「Supervisory Developments」一节横跨 p.35–54，自动拆出 19 个子节点。「Enforcement Actions」（p.41–42）就是这样来的，检索时能直接命中它。

④ 摘要与文档描述

  • 叶子节点：2–4 句的 summary，写明涵盖的主题、实体、指标、表格和期间，目的是让 LLM 只看目录就能判断该不该读这一节。原文过长时取开头和结尾，约 6k token。
  • 父节点：用标题到第一个子节点之间的引言写 1–2 句 prefix_summary（引言太短就跳过）。
  • 文档：用两层大纲加前两页，写 2–3 句 description，供多文档检索时挑文档用。
  • 所有节点并发处理（默认并发 24）。

⑤ 节点和页向量

每个节点算一个 bge-m3 向量（SiliconFlow），内容是「文件路径 + 标题路径 + 摘要」，例如 02_财务/2025年度预算.xlsx · 电站清单：……。文档描述也算一个。一份 200 页的文档约 100 个节点，几秒钟、几乎不花钱。向量服务不可用时跳过，检索自动退回纯 LLM 读树；之前索引的文档在服务启动时自动补算向量。

每一页也算一个向量，内容是「文件路径 · 页标签 / 所在章节路径 / 页文本」，给页面检索（POST /v1/pages/search）用：页面得分 = 0.7 × 页向量相似度 + 0.3 × 覆盖这一页的章节节点的相似度，全程不调 LLM，全库 600 多页约 0.2 秒。

zip 资料包

POST /v1/collections 上传 zip。目录结构变成一棵目录树，每个支持格式的文件是一个普通文档：单独建索引，有自己的页、树和引用。全部文件索引完后，由下往上给每个目录写 1–2 句摘要（依据子目录摘要和文件描述）。

  • 只有一个顶层目录时，把它当作根，不多出一层。
  • 没有 UTF-8 标志的文件名按 GBK 解码（中文 Windows 打的包）。__MACOSX、隐藏文件、~$ 临时文件直接忽略；不支持的格式、损坏的文件记进 skipped。
  • 文件按生成的 id 写盘，压缩包里的路径不会落到文件系统上；文件数、单文件大小、解压总大小都有上限。

检索 pidx/search.py

① 选文档

指定了 doc_ids 就只搜这些文档，指定了 collection_id 就只搜这个资料包，否则搜全库。超过 1 篇时：先算问题向量，按「文档描述相似度、文档里最相似节点的相似度」两者取大给文档排序，取前 30 篇；再让 LLM 读这些候选，挑出需要查的（最多 5 篇，对比类问题会挑多篇）。资料包里的文件以目录树的形式给 LLM：目录名、目录摘要，下面是文件名和文件描述。

② 树检索

把树渲染成缩进文本，每行是 [node_id] 标题 (p.起-止) — 摘要，交给 LLM。它返回一段推理（答案应该在哪、为什么）和最多 top_k 个节点 id。提示词要求它优先选最具体的节点；对比、合计、定义、脚注这类信息可能分散在几处的问题，要多选几个。有两种方式（请求参数 retrieval，默认 hybrid）：

hybrid向量召回子树 + LLM 并行读：把树切成若干锚点子树，每棵的骨架不超过约 3000 token。做法是从根往下走：放得下的相邻兄弟节点打包成一棵；放不下的节点自己不进包，它的子节点继续往下切，它本身作为祖先行显示在每棵子树的上方（也可以被选中）。所以子树的深度不是写死的，由树的大小决定。检索时，用问题向量给所有节点打分，子树的分数取其中最高的节点；每篇文档取前 3 棵，并行各发一次 LLM 调用，让它读这棵子树、给出相关度（0–3）和要读的节点。最后按相关度、再按各子树内的顺序轮流合并，取前 top_k 个。
例：美联储年报 108 个节点、骨架约 1.6 万 token，切成 13 棵子树。「Enforcement Actions」那道题并行读了 3 棵子树，整题（含作答）输入 8.9k token；读整棵树要 29.5k token。

treeLLM 读整棵树：树骨架不超过 4 万 token 时一次给全；更大的树先只展开两层，其余标成 collapsed，LLM 可以要求展开感兴趣的节点，最多交互 4 轮。没有向量时也走这条路。

  • 如果同时选中了一个节点和它的祖先：祖先的原文不超过 1.2 万 token 就只读祖先，否则只读更具体的子孙，避免同一段原文读两遍。
  • 多文档时，各文档的树检索并行进行。

③ 读原文

选中节点的原文不是整段塞进去，而是按版面块排列，每块前面加上标签，例如 [1:p42_b2] In 2023, the Federal Reserve completed 63 formal enforcement actions…（1 是文档序号，p42_b2 是第 42 页第 2 块）。读取预算是每个节点 1.2 万 token、总共 6 万 token，超出的部分会截断并注明。

④ 作答与补搜

LLM 只能依据这些原文作答，并在论断后面附上块标签。答案以 markdown 流式输出，最后一行是 @@STATUS@@ {"sufficient", "missing"}（这一行不会推送给前端）：

  • sufficient=false 时，把"已经读过哪些节点、还缺什么"写进下一轮树检索的提示词，排除已读节点再找一轮（max_rounds，默认 2）。hybrid 模式下，用「问题 + 缺什么」重新算向量，召回上一轮没读过的子树。
  • 答案里的块标签会映射回 {doc_id, page, block_id, bbox, text}，bbox 用千分比坐标，演示页据此在原页图上高亮。
  • 库里没有答案时，它会明确说没有。演示页里的「不编造」那道题就是测这个的。

已知局限

  • 图只在建索引时看一次：视觉模型的识别结果是固定的文字，检索时不会带着问题回头再看图；识别漏掉的细节就答不出来。Office 文件里的图还没有识别。
  • OCR 额度：云端 MinerU 每天有 1000 页高优先级额度，大批量扫描件超出后会排队变慢。
  • 字体信息坏掉的 PDF只能走策略 3，层级偶尔会放错（four-lectures.pdf 的第 3 章就有这个问题）。
  • 延迟：检索用 DeepSeek 时，13 道推荐问题平均 3.6 秒（hybrid）/ 4.0 秒（tree），hybrid 平均输入 token 约为 tree 的一半；用 Atria 时平均 37 秒。大部分时间花在逐 token 生成上，详见演示页每次问答最后的瀑布图。
  • Office 文件没有原页高亮：MinerU 不给 Office 的版面坐标，引用打开的是解析出的文本；「页」是按大小切的虚拟页。
  • 还没有系统评测：目前只人工核对了演示页上的推荐问题。下一步用 10-K 问答集和向量 RAG、开源 PageIndex 做对比。
